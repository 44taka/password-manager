# ADR 0007: エラーハンドリングとロギングの統合設計

## Status
Accepted

## Date
2026-05-13

## Context
アプリケーションの規模拡大に伴い、問題の診断やユーザー体験の向上のため、堅牢なエラーハンドリングとロギングの仕組みが必要となった。これまではエラーハンドリングが散発的であり、体系的なログ出力も存在していなかった。

## Decision
階層化された例外クラスと統合ロギングシステムを導入する。

### 1. 例外階層の構築
- 全レイヤー共通の基底例外 `AppError` を `core` 層に定義する。これによりプレゼンテーション層での一括捕捉を可能にする。
- レイヤーごとの基底例外を定義する：
    - ドメイン層: `DomainError`（ビジネスロジックやバリデーションエラー用）
    - インフラ層: `InfrastructureError`（技術的なエラーや外部サービス失敗用）
- 具体的な例外はこれらを継承する（例: `ValidationError`, `DatabaseError`, `KeyringError`）。
- 規約に従い、各例外クラスは「1クラス1ファイル」で定義する。

### 2. ロギング戦略
- `core/logger.py` に設定を集約する。
- **JSON形式の出力**: 構造化されたログ（timestamp, level, layer, event, message, context）を出力し、解析を容易にする。
- `TimedRotatingFileHandler` を使用し、ログを日次でローテートする。
- ファイル名には日付を含める（例: `app-2026-05-13.log`）。
- Sentry 統合をサポートし、環境変数 `SENTRY_DSN` が設定されている場合にバックグラウンドでエラーを追跡する。

### 3. アトミック性と補償トランザクション
- `UnifiedAccountRepository` において、Keychain と SQLite の更新のアトミック性を保証する。
- **Keychain更新を先に実行**し、その後の SQLite 更新が失敗した場合は、Keychain の変更をロールバック（新規なら削除、更新なら旧値への復旧）する。

### 4. プレゼンテーション層のUI通知
- Presenter で `AppError` を捕捉し、`MainWindow.show_error_message` を通じてユーザーに通知する。

## Rationale
- ✅ **追跡性の向上**: JSON形式の構造化ログにより、エラーの発生箇所や文脈（レイヤー、イベント）が特定しやすくなる。
- ✅ **データ不整合の防止**: Keychain と SQLite の間の補償トランザクションにより、パスワードとメタデータの不一致を防ぐ。
- ✅ **責務の明確化**: 例外の階層化により、どのレイヤーで発生した問題かをコード上で明確に区別できる。

## Consequences

### Positive
- ログ解析ツール（Sentry 等）との親和性が高まり、本番環境での問題解決が迅速になる。
- 補償トランザクションにより、複雑な永続化処理の信頼性が向上する。

### Negative
- 「1クラス1ファイル」方針により、ファイル数が増加する。
- JSON形式のため、人間が直接 `cat` 等で読む際には少し読みづらくなる可能性がある。

### Neutral
- ログ出力時に `event` や `context` を意識して記述するスタイルが求められる。
