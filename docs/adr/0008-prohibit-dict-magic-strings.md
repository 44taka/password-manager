# ADR 0008: 辞書型（マジックストリング）によるデータ受け渡しの禁止

## Status
Accepted

## Date
2026-05-24

## Context
リポジトリ層やデータアクセス層（インフラ層）において、異なるモジュールやクラス間でのデータ転送に `dict[str, Any]` を多用していた。
しかし、辞書型を使用すると `data["site_name"]` のようにキーを文字列（マジックストリング）で記述することになり、以下の問題が発生する。
- キー名をタイポしていても、静的型チェック（Pyright等）やリンターで検知できず、実行時に初めてエラーになる。
- エディタのコード補完（オートコンプリート）が効かないため、開発効率が低下する。
- DBスキーマやフィールド名の変更時、参照箇所の特定が難しくリファクタリングの難易度が上がる。

## Decision
- クラス間やレイヤー間でのデータ受け渡しにおいて、`dict[str, Any]` に依存したマジックストリングによるアクセスを原則禁止とする。
- 代わりに、以下の型定義されたオブジェクトを使用してデータを転送し、プロパティアクセス（例: `data.site_name`）を行う。
  1. ORMモデルクラス (例: `SqliteAccountModel`)
  2. Pydanticモデルクラス
  3. Python標準の `dataclass`
- データベースアクセスを行うストアクラス（例: `SqliteAccountStore`）の戻り値は、辞書型ではなくORMモデルクラスを直接返却するよう設計する。

## Rationale
- ✅ **型安全性の向上**: 静的解析ツールによってタイポや型ミスマッチをコンパイル/チェック段階で 100% 検出できるようになる。
- ✅ **開発効率の向上**: エディタのオートコンプリートがフルに機能し、開発者がフィールド名を記憶する必要がなくなる。
- ✅ **堅牢なリファクタリング**: 属性名を変更する際、影響範囲をIDEのリネーム機能などで一瞬かつ確実に特定できる。

## Consequences

### Positive
- データ構造とコード間の紐付けが厳密になり、実行時例外（`KeyError` 等）の発生リスクが大幅に減少する。
- 静的型チェックの恩恵を最大化できる。

### Negative
- ごく小規模なデータ転送であっても `dataclass` などを別途定義する必要があり、定義ファイルやファイル記述量がわずかに増加することがある。

### Neutral
- 特になし。
